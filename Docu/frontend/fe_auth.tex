\section{Authentifizierungsflow: Registrierung und E-Mail-Bestätigung}

Der Authentifizierungsprozess von EduShelf umfasst drei aufeinander aufbauende Schritte: die Erstellung eines neuen Benutzerkontos, die Verifikation der E-Mail-Adresse sowie den eigentlichen Login. Dieser Ablauf stellt sicher, dass nur Nutzer mit einer verifizierten Identität Zugang zur Plattform erhalten.

Die Komponente \texttt{Register.jsx} realisiert ein zweistufiges Validierungskonzept. Zunächst wird die Benutzereingabe vollständig clientseitig geprüft, bevor anschließend eine Anfrage an den Server gesendet wird. Dies reduziert unnötige Netzwerkanfragen und gibt dem Nutzer sofortiges Feedback.

\subsubsection{Clientseitige Validierung}

Bei diesem Teil der Validierung werden alle Felder nach klar definierten Regeln überprüft:

\begin{lstlisting}[language=JavaScript, caption={Clientseitige Validierung der Eingaben}]
const validate = () => {
  const newErrors = {};
  if (!username || username.length < 3 || username.length > 20) {
    newErrors.username = 'Username must be between 3 and 20 characters.';
  }
  if (!email || !/\S+@\S+\.\S+/.test(email)) {
    newErrors.email = 'A valid email address is required.';
  }
  if (!password || password.length < 6) {
    newErrors.password = 'Password must be at least 6 characters long.';
  }
  setErrors(newErrors);
  return newErrors;
};
\end{lstlisting}

Diese Methode setzt auf Regex zur E-Mail-Validierung und Längenprüfungen für Benutzername und Passwort. Nur wenn \texttt{validate()} ein leeres Fehlerobjekt zurückgibt, wird die Backend-Anfrage ausgelöst.

\subsubsection{Serverseitige Fehlerverarbeitung}

Serverseitige Fehler (z.\,B. ein bereits verwendeter Benutzername) werden strukturiert verarbeitet. Das Backend sendet ein Fehlerobjekt mit feldspezifischen Nachrichten zurück, welches das Frontend auflöst und den entsprechenden Feldern zuordnet:

\begin{lstlisting}[language=JavaScript, caption={Verarbeitung von Backend-Validierungsfehlern}]
if (error.response?.data?.errors) {
  const backendErrors = {};
  for (const key in error.response.data.errors) {
    // Schluessel mit Kleinbuchstaben normalisieren (z.B. "Username" -> "username")
    const formattedKey = key.charAt(0).toLowerCase() + key.slice(1);
    backendErrors[formattedKey] = error.response.data.errors[key].join(' ');
  }
  setErrors(backendErrors);
}
\end{lstlisting}

\subsection{Login-Prozess (Login.jsx)}

\begin{figure}[h]
    \centering
    \includegraphics[width=0.6\textwidth]{img/login-dark-mode}
    \caption{Login-Ansicht von EduShelf im Dark-Mode}
    \label{fig:login}
\end{figure}

Der Login-Prozess ist bewusst in zwei Abfragen gegliedert: Zuerst wird ein POST-Request an \texttt{/Users/login} gesendet. Bei Erfolg antwortet das Backend mit einem \texttt{HttpOnly}-Session-Cookie~\cite{MDNHttpOnlyCookie} und den Benutzerdaten. Unmittelbar danach erfolgt ein zweiter Aufruf an \texttt{/Users/\{id\}/roles}, da die Rollenzuweisung (\textit{Admin}, \textit{User}) bestimmt, welche Menüpunkte in der Navigation sichtbar sind.

Das kombinierte Benutzerobjekt (Daten + Rolle) wird im \texttt{localStorage}~\cite{MDNLocalStorage} hinterlegt, um den Anmeldestatus über Browser-Refreshes hinweg zu erhalten. Diese Persistenzmaßnahme dient ausschließlich der UI-Zustandsverwaltung -- der tatsächliche Sicherheitsanker ist der \texttt{HttpOnly}-Cookie. Da der \texttt{localStorage} vom Nutzer manipulierbar ist, wird er explizit nicht als Sicherheitsmechanismus genutzt: Bei jeder Initialisierung der App erfolgt ein Abgleich mit \texttt{/Users/me} gegen den serverseitigen Cookie.

\subsection{E-Mail-Bestätigung}

Nach der Registrierung erhält der Nutzer eine Bestätigungs-E-Mail. Der enthaltene Link führt zur Komponente \texttt{VerifyEmail.jsx}, welche den Token aus der URL extrahiert und an den Backend-Endpunkt zur Verifikation übermittelt. Da das Backend den Link selbst generiert, enthält das Frontend lediglich die Anzeigelogik für die Erfolgs- bzw. Fehlermeldung -- eine klare Umsetzung des Single-Responsibility-Prinzips.
