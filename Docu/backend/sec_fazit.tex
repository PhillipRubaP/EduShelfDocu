\section{Fazit}
Das Backend von EduShelf stellt ein robustes, modernes und erweiterungsfähiges Fundament für die Lernplattform dar. Die während der Entwicklung getroffenen Architekturentscheidungen haben sich als funktional erwiesen, um die Anforderungen einer KI-gestützten Dokumentenverwaltungsplattform zu erfüllen.

\subsection{Erreichte Ziele}
\begin{itemize}
    \item \textbf{Vollständige RAG-Pipeline:} Die Kombination aus semantischer Vektorsuche (pgvector + HNSW-Index), Intent-Erkennung und tokenbasierter Kontextlimitierung ermöglicht präzise, dokumentenspezifische KI-Antworten ohne externe API-Abhängigkeiten.
    \item \textbf{Datenschutz durch lokale KI:} Der Einsatz von Ollama als lokaler LLM-Server stellt sicher, dass keine Dokumenteninhalte das eigene System verlassen. Dies ist insbesondere für Bildungseinrichtungen relevant.
    \item \textbf{Robuste Lerninhaltsgenerierung:} Sowohl die Flashcard- als auch die Quiz-Generierung sind durch mehrstufige JSON-Parsing-Strategien widerstandsfähig gegenüber variierenden LLM-Antwortschemas.
    \item \textbf{Sicherheit:} Der vollständige E-Mail-Verifizierungsflow, BCrypt-Passwort-Hashing, HttpOnly-Cookie-Authentifizierung und RBAC schaffen eine mehrschichtige Sicherheitsarchitektur.
    \item \textbf{Infrastruktur:} Die vollständige Containerisierung mit Docker Compose erlaubt ein reproduzierbares, portables Deployment auf jedem Linux-Server ohne manuelles Setup.
    \item \textbf{Teststrategie:} Die Testklassen mit Unit und Integrationstests decken alle sicherheits- und geschäftskritischen Pfade ab.
\end{itemize}

\subsection{Lernerkenntnisse und Herausforderungen}
Die größte technische Herausforderung war die \textbf{Unvorhersehbarkeit von LLM-Ausgaben}: Trotz präziser System-Prompts und expliziter JSON-Formatvorgaben weichen Sprachmodelle gelegentlich vom erwarteten Schema ab. Die Lösung lag nicht im Erzwingen einer bestimmten Ausgabe, sondern in der Implementierung mehrerer Fallback-Strategien im Parsingabschnitt liegt.

Ein weiteres Lernfeld war die \textbf{Performance-Optimierung der Ingestion-Pipeline}: Das ursprüngliche Ansatz, Dokumente synchron im HTTP-Request-Zyklus zu verarbeiten, führte bei großen PDFs zu Timeouts. Die Einführung einer \texttt{BackgroundJobQueue} mit asynchroner Verarbeitung löste dieses Problem ohne die Architektur grundlegend zu verändern.

\subsection{Mögliche Erweiterungen}
\begin{itemize}
    \item \textbf{Streaming-Responses:} Die aktuelle Implementierung wartet auf die vollständige LLM-Antwort. Eine WebSocket-Anbindung würde die wahrgenommene Latenz deutlich reduzieren.
    \item \textbf{Multi-Tenant-Unterstützung:} Aktuell ist jeder User vollständig isoliert. Eine optionale Kurs- oder Gruppenebene wäre eine mögliche Erweiterung.
    \item \textbf{Mikroservice-Migration:} Der aktuelle Ansatz war für die Initialentwicklung ideal. Bei steigender Last könnten rechenintensive Services (Indexierung, KI-Inferenz) als eigenständige Mikroservices ausgelagert werden.
\end{itemize}
