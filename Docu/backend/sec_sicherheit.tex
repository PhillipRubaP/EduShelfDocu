\section{Sicherheitskonzepte}

\subsection{Authentifizierung \& Autorisierung}
Die Authentifizierung erfolgt über Cookies (\texttt{CookieAuthenticationDefaults}).
\begin{itemize}
    \item \textbf{Login-Prozess:} Der Nutzer sendet Anmeldedaten an \texttt{POST /api/users/login}. Der \texttt{AuthService} lädt den Benutzer inklusive seiner Rollen aus der Datenbank und überprüft den Passwort-Hash mittels BCrypt. Zusätzlich wird geprüft, ob die E-Mail-Adresse bereits bestätigt wurde -- nicht-verifizierte Accounts können sich nicht einloggen.
    \item \textbf{Claims-Based Identity:} Bei erfolgreichem Login werden Claims (kryptographisch signierte Aussagen) über den Benutzer in das Cookie eingebettet: Benutzer-ID (\texttt{ClaimTypes.NameIdentifier}), E-Mail, Benutzername und alle zugewiesenen Rollen (\texttt{ClaimTypes.Role}). Diese Claims stehen serverseitig bei jedem Request über \texttt{HttpContext.User} zur Verfügung.
    \item \textbf{Session-Lebensdauer:} Das Cookie ist auf 120 Minuten befristet (\texttt{IsPersistent = true, ExpiresUtc = +120 min}).
    \item \textbf{Middleware:} Die Standard-ASP.NET Core Authentifizierungs-Middleware entschlüsselt das Cookie bei jedem Request und rekonstruiert das \texttt{ClaimsPrincipal}-Objekt.
\end{itemize}

\begin{lstlisting}[language={[Sharp]C}, caption={Claims-Aufbau beim Login in AuthService.cs}]
var claims = new List<Claim>
{
    new Claim(ClaimTypes.NameIdentifier, user.UserId.ToString()),
    new Claim(ClaimTypes.Email, user.Email),
    new Claim(ClaimTypes.Name, user.Username)
};
foreach (var userRole in user.UserRoles)
    claims.Add(new Claim(ClaimTypes.Role, userRole.Role.Name));
var claimsIdentity = new ClaimsIdentity(
    claims, CookieAuthenticationDefaults.AuthenticationScheme);
var authProperties = new AuthenticationProperties
{
    IsPersistent = true,
    ExpiresUtc = DateTimeOffset.UtcNow.AddMinutes(120)
};
await _httpContextAccessor.HttpContext.SignInAsync(
    CookieAuthenticationDefaults.AuthenticationScheme,
    new ClaimsPrincipal(claimsIdentity),
    authProperties);
\end{lstlisting}

\subsection{Rollenbasiertes Zugriffssystem (RBAC)}
EduShelf implementiert ein einfaches, aber effektives Role-Based Access Control System. Rollen (\texttt{Student}, \texttt{Admin}) werden in der Tabelle \texttt{Roles} gespeichert und über die Join-Tabelle \texttt{UserRoles} Nutzern zugewiesen.

Jeder neu registrierte Nutzer erhält automatisch die Rolle \texttt{Student}. Die Rolle wird beim Erstellen des Nutzers aus der Datenbank geladen und dem \texttt{UserRoles}-Set hinzugefügt:

\begin{lstlisting}[language={[Sharp]C}, caption={Automatische Rollenzuweisung bei der Registrierung}]
var studentRole = await _context.Roles
    .SingleOrDefaultAsync(r => r.Name == Roles.Student);
user.UserRoles.Add(new UserRole { Role = studentRole });
\end{lstlisting}

In den Controllern wird die Autorisierung deklarativ über Attribute gesteuert:
\begin{itemize}
    \item \texttt{[Authorize]} -- Nur eingeloggte Nutzer (jede Rolle).
    \item \texttt{[Authorize(Roles = \char`\"Admin\char`\")]} -- Nur Administratoren (z.B. für Nutzer-Löschung oder Tag-Verwaltung).
\end{itemize}

\subsection{E-Mail-Verifizierung}
Bei der Registrierung wird ein kryptographisch sicherer Bestätigungstoken (32 Byte, hexadezimal kodiert, 24 Stunden gültig) generiert und per E-Mail an den Nutzer gesendet. Schlägt der E-Mail-Versand fehl, wird der Nutzer-Datensatz sofort wieder gelöscht -- das System verhält sich somit \textit{atomar}. Bei Klick auf den Bestätigungslink führt der \texttt{AuthService} vier Prüfungen durch:

\begin{enumerate}
    \item Nutzer mit dieser E-Mail existiert.
    \item E-Mail ist noch nicht bestätigt.
    \item Der übermittelte Token stimmt exakt mit dem gespeicherten überein.
    \item Der Token ist nicht abgelaufen (\texttt{ExpiresAt > DateTime.UtcNow}).
\end{enumerate}

Bei Erfolg werden \texttt{IsEmailConfirmed = true} gesetzt und Token sowie Ablaufzeit aus der Datenbank gelöscht. Zusätzlich werden alle eingehenden Daten mittels \textit{FluentValidation} automatisch vor dem Controller-Aufruf validiert -- ungültige Anfragen werden sofort mit HTTP 400 und einer strukturierten Fehlerliste abgelehnt.
