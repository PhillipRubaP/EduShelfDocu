\subsection{Unit Tests (xUnit + Moq)}
Die Geschäftslogik (Services) wird isoliert getestet. Externe Abhängigkeiten wie Datenbank, LLM oder E-Mail-Dienst werden mittels \texttt{Moq} durch kontrollierte Testdoubles ersetzt. Die Datenbank wird für jeden Testfall durch eine separate In-Memory-Datenbankinstanz (über \texttt{UseInMemoryDatabase} mit \texttt{Guid.NewGuid()}) vollständig isoliert.

\subsubsection{Beispiel: FlashcardService}
Die drei Kerntests des \texttt{FlashcardService} illustrieren das typische Testmuster:

\begin{lstlisting}[language={[Sharp]C}, caption={Unit Test: Erfolgreiche Flashcard-Generierung}]
[Fact]
public async Task GenerateFlashcardsAsync_ValidContent_ShouldCreateFlashcards()
{
    // Arrange -- Mock-LLM gibt valides JSON zurueck
    var jsonResponse = "[{\"Question\": \"What is AI?\", \"Answer\": \"Artificial Intelligence\"}," +
                       " {\"Question\": \"Is it cool?\", \"Answer\": \"Yes\"}]";
    _mockChatCompletionService
        .Setup(c => c.GetChatMessageContentsAsync(...))
        .ReturnsAsync(new List<ChatMessageContent> { new(AuthorRole.Assistant, jsonResponse) });

    // Act
    var result = await service.GenerateFlashcardsAsync(request, userId);

    // Assert
    Assert.Equal(2, result.ToList().Count);
    Assert.Equal(2, context.Flashcards.Count());
    Assert.Single(context.Tags); // Tag "Test Doc" automatisch erstellt
}
\end{lstlisting}

\begin{lstlisting}[language={[Sharp]C}, caption={Unit Test: Leerer Dokumenteninhalt wirft BadRequestException}]
[Fact]
public async Task GenerateFlashcardsAsync_NoContent_ShouldThrowBadRequest()
{
    _mockDocumentService.Setup(d => d.GetDocumentContentAsync(1, userId, Roles.Student))
        .ReturnsAsync(""); // Leerer Inhalt
    await Assert.ThrowsAsync<BadRequestException>(
        () => service.GenerateFlashcardsAsync(request, userId));
}
\end{lstlisting}

\begin{lstlisting}[language={[Sharp]C}, caption={Unit Test: Ungültiges JSON vom LLM wirft KernelServiceException}]
[Fact]
public async Task GenerateFlashcardsAsync_InvalidJsonFromAI_ShouldThrowKernelServiceException()
{
    // Mock-LLM gibt Text statt JSON zurueck
    var badResponse = new ChatMessageContent(AuthorRole.Assistant, "This is not JSON");
    _mockChatCompletionService.Setup(...).ReturnsAsync(new List<ChatMessageContent> { badResponse });

    await Assert.ThrowsAsync<KernelServiceException>(
        () => service.GenerateFlashcardsAsync(request, userId));
}
\end{lstlisting}

\subsubsection{Beispiel: AuthService}
Der \texttt{AuthService} wird ebenfalls umfassend getestet, inklusive des E-Mail-Bestätigungsflows:

\begin{lstlisting}[language={[Sharp]C}, caption={Unit Test: Registrierung erstellt Nutzer und sendet E-Mail}]
[Fact]
public async Task RegisterUserAsync_ValidData_ShouldCreateUserAndSendEmail()
{
    var result = await service.RegisterUserAsync(registerDto);

    Assert.Single(context.Users);
    Assert.False((await context.Users.FirstAsync()).IsEmailConfirmed);
    Assert.NotNull((await context.Users.FirstAsync()).EmailConfirmationToken);

    // Verifiziert: E-Mail wurde genau einmal an die richtige Adresse gesendet
    _mockEmailService.Verify(
        x => x.SendEmailAsync("new@example.com", It.IsAny<string>(), It.IsAny<string>()),
        Times.Once);
}
\end{lstlisting}

\begin{lstlisting}[language={[Sharp]C}, caption={Unit Test: Abgelaufener Token wirft BadRequestException}]
[Fact]
public async Task ConfirmEmailAsync_ExpiredToken_ShouldThrowBadRequest()
{
    var user = new User
    {
        EmailConfirmationToken = "expired_token",
        EmailConfirmationTokenExpiresAt = DateTime.UtcNow.AddHours(-1) // in der Vergangenheit
    };
    context.Users.Add(user);

    await Assert.ThrowsAsync<BadRequestException>(
        () => service.ConfirmEmailAsync(confirmDto));
}
\end{lstlisting}

\subsection{Validatoren-Tests}
\texttt{FluentValidation}-Regeln werden mit der Bibliotheksmethode \texttt{TestValidate} isoliert geprüft -- kein HTTP-Stack nötig:

\begin{lstlisting}[language={[Sharp]C}, caption={Validator-Tests mit FluentValidation.TestHelper}]
[Fact]
public void Should_Have_Error_When_Email_Is_Invalid()
{
    var model = new UserRegister { Username = "user", Email = "invalid_email", Password = "pw" };
    var result = _validator.TestValidate(model);
    result.ShouldHaveValidationErrorFor(x => x.Email);
}

[Fact]
public void Should_Not_Have_Error_When_Model_Is_Valid()
{
    var model = new UserRegister { Username = "validUser", Email = "test@example.com",
                                   Password = "strongPassword123" };
    _validator.TestValidate(model).ShouldNotHaveAnyValidationErrors();
}
\end{lstlisting}

\subsection{Integration Tests}
Für Controller und die Datenbankinteraktion werden Integrationstests verwendet. Hierbei wird mittels \texttt{WebApplicationFactory} ein echter Test-Server im Speicher hochgefahren, der gegen den vollständigen ASP.NET Core Middleware-Stack (Routing, Authentifizierung, Fehlerbehandlung) und eine separate In-Memory-Datenbankinstanz läuft. Dies stellt sicher, dass das Routing, die Autorisierungsattribute und das Entity Framework korrekt zusammenspielen -- unabhängig voneinander, aber als zusammenhängendes System.

\subsection{Testabdeckung und Teststrategie}
Eine automatisierte Messung der Code-Abdeckung ergibt eine \textbf{Zeilenabdeckung von 5\,\%} und eine \textbf{Branch-Abdeckung von 20{,}1\,\%}. Diese Werte sind bewusst nicht das primäre Optimierungsziel der Teststrategie und bedürfen einer Einordnung.

Der Großteil des Backends besteht aus Komponenten, die strukturell schwer automatisiert zu instrumentieren sind: Infrastruktur-Code (Docker-Konfiguration, Datenbankmigrationen, \texttt{Program.cs}-Bootstrapping), I/O-gebundene Operationen (Dateisystem-Zugriffe, HTTP-Aufrufe an externe Dienste) sowie die Integration mit dem lokalen LLM via Ollama. Diese Bereiche sind im klassischen Sinne nicht unit-testbar, ohne den gesamten Infrastruktur-Stack hochzufahren -- was außerhalb des Umfangs eines Hochschulprojekts liegt.

Der Fokus der Tests lag daher gezielt auf den \textbf{kritischen Geschäftslogik-Pfaden}: Registrierungs- und Authentifizierungsflows, KI-Generierung mit Fehlerbehandlung (ungültiges JSON, leere Dokumente), Intent-Erkennung, Token-Limitierung sowie das Routing und die Autorisierungs\-logik der Controller. Diese Bereiche repräsentieren die fehlersensibelsten Stellen der Anwendung, in denen ein Fehler direkte Auswirkungen auf Sicherheit oder Datenintegrität hätte -- und sind daher vollständig abgedeckt.

Die gemessene Abdeckungsquote spiegelt somit die Architektur der Anwendung wider, nicht eine mangelnde Testdisziplin: Eine höhere Gesamtabdeckung wäre nur durch aufwändige Infrastruktur-Mocks oder End-to-End-Tests erreichbar, die den Rahmen dieses Projekts übersteigen würden.
