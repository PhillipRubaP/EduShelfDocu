\subsection{Unit Tests (xUnit + Moq)}
Die Geschäftslogik (Services) wird isoliert getestet. Externe Abhängigkeiten wie Datenbank, LLM oder E-Mail-Dienst werden mittels \texttt{Moq} durch kontrollierte Testdoubles ersetzt. Die Datenbank wird für jeden Testfall durch eine separate In-Memory-Datenbankinstanz (über \texttt{UseInMemoryDatabase} mit \texttt{Guid.NewGuid()}) vollständig isoliert.

\newpage
\subsubsection{Beispiel: FlashcardService}
Die drei Kerntests des \texttt{FlashcardService} zeigen das typische Testmuster:

\begin{lstlisting}[language={[Sharp]C}, caption={Unit Test: Erfolgreiche Flashcard-Generierung}]
[Fact]
public async Task GenerateFlashcardsAsync_ValidContent_ShouldCreateFlashcards()
{
    // Arrange -- Mock-LLM gibt valides JSON zurueck
    var jsonResponse = "[{\"Question\": \"What is AI?\", \"Answer\": \"Artificial Intelligence\"}," +
                       " {\"Question\": \"Is it cool?\", \"Answer\": \"Yes\"}]";
    _mockChatCompletionService
        .Setup(c => c.GetChatMessageContentsAsync(...))
        .ReturnsAsync(new List<ChatMessageContent> { new(AuthorRole.Assistant, jsonResponse) });

    // Act
    var result = await service.GenerateFlashcardsAsync(request, userId);

    // Assert
    Assert.Equal(2, result.ToList().Count);
    Assert.Equal(2, context.Flashcards.Count());
    Assert.Single(context.Tags); // Tag "Test Doc" automatisch erstellt
}
\end{lstlisting}

\subsubsection{Beispiel: AuthService}
Der \texttt{AuthService} wird ebenfalls umfassend getestet, inklusive des E-Mail-Bestätigungsflows:

\begin{lstlisting}[language={[Sharp]C}, caption={Unit Test: Registrierung erstellt Nutzer und sendet E-Mail}]
[Fact]
public async Task RegisterUserAsync_ValidData_ShouldCreateUserAndSendEmail()
{
    var result = await service.RegisterUserAsync(registerDto);

    Assert.Single(context.Users);
    Assert.False((await context.Users.FirstAsync()).IsEmailConfirmed);
    Assert.NotNull((await context.Users.FirstAsync()).EmailConfirmationToken);

    // Verifiziert: E-Mail wurde genau einmal an die richtige Adresse gesendet
    _mockEmailService.Verify(
        x => x.SendEmailAsync("new@example.com", It.IsAny<string>(), It.IsAny<string>()),
        Times.Once);
}
\end{lstlisting}

\subsection{Validatoren-Tests}
\texttt{FluentValidation}-Regeln werden mit der Bibliotheksmethode \texttt{TestValidate} isoliert geprüft:

\begin{lstlisting}[language={[Sharp]C}, caption={Validator-Tests mit FluentValidation.TestHelper}]
[Fact]
public void Should_Have_Error_When_Email_Is_Invalid()
{
    var model = new UserRegister { Username = "user", Email = "invalid_email", Password = "pw" };
    var result = _validator.TestValidate(model);
    result.ShouldHaveValidationErrorFor(x => x.Email);
}

[Fact]
public void Should_Not_Have_Error_When_Model_Is_Valid()
{
    var model = new UserRegister { Username = "validUser", Email = "test@example.com",
                                   Password = "strongPassword123" };
    _validator.TestValidate(model).ShouldNotHaveAnyValidationErrors();
}
\end{lstlisting}

\subsection{Integration Tests}
Für Controller und die Datenbankinteraktion werden Integrationstests verwendet. Hierbei wird mittels \texttt{WebApplicationFactory} ein echter Test-Server im Speicher hochgefahren, der gegen den vollständigen ASP.NET Core Middleware-Stack (Routing, Authentifizierung, Fehlerbehandlung) und eine separate In-Memory-Datenbankinstanz läuft. Dies stellt sicher, dass das Routing, die Autorisierungsattribute und das Entity Framework korrekt zusammenspielen, unabhängig voneinander, aber als zusammenhängendes System.
